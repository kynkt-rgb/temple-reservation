## 1. システム構成

### 1.1 全体構成

```
[寺務所のPC（ブラウザ）]
        │ HTTP（80番）で EC2 のパブリックIPにアクセス
        ▼
┌──────────────── AWS（東京リージョン）────────────────┐
│  VPC                                                 │
│  ┌─ パブリックサブネット ─────────────────────────┐ │
│  │  EC2（Elastic IP）                             │ │
│  │   Nginx :80                                    │ │
│  │    ├─ /      → Next.js   :3000                 │ │
│  │    └─ /api/  → Rails(Puma) :3001               │ │
│  └────────────────────────────────────────────────┘ │
│                   │ 3306（EC2のセキュリティグループのみ）│
│  ┌─ プライベートサブネット（2つのAZ）─────────────┐ │
│  │  RDS for MySQL 8.4                             │ │
│  └────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────┘
```

- 1台のEC2で Nginx・Next.js・Rails を動かす。Nginx がURLのパスで振り分けるため、ブラウザから見るとフロントとAPIは同じアクセス先（同じIPアドレス）になる（CORS設定は不要）。
- DBはRDSに置き、EC2からだけ接続できるようにする。

### 1.2 採用技術

| 区分 | 技術 | 補足 |
| --- | --- | --- |
| フロントエンド | Next.js（App Router）+ TypeScript | 画面はクライアント側でAPIを呼び出して描画する |
| スタイル | Tailwind CSS | |
| 祝日判定 | `@holiday-jp/holiday_jp`（npm） | カレンダーで祝日に色を付けるために使う |
| バックエンド | Ruby on Rails（APIモード） | アプリサーバーは Puma |
| データベース | MySQL 8.4（長期サポート版）。本番は RDS、開発は手元の Mac | CHECK 制約を使う |
| Webサーバー | Nginx | リバースプロキシ（HTTPS化はしない。9.3 参照） |
| インフラ構築 | Terraform | 状態ファイルは S3 に保存 |

各ソフトのバージョンは、実装を始める時点の安定版（LTS があれば LTS）にそろえる。

├── docs/        要件定義書・基本設計書
├── frontend/    Next.js
├── backend/     Rails（APIモード）
└── infra/       Terraform

### 2.4 SC-01 月カレンダー

要件「見開きで1か月を見渡せる」に合わせ、**縦に日付、横に時間枠** を並べた表にする。

```
        ◀ 前月     2026年11月     翌月 ▶    [今月]
┌──────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
│ 日付 │  10時    │  11時    │  12時    │  13時    │  14時    │  15時    │
├──────┼──────────┼──────────┼──────────┼──────────┼──────────┼──────────┤
│ 1 日 │          │山田様    │          │          │          │          │
│      │          │一周忌    │          │          │          │          │
│      │          │お寺/住職 │          │          │          │          │
├──────┼──────────┼──────────┼──────────┼──────────┼──────────┼──────────┤
│ 2 月 │佐藤様    │          │          │【葬儀】  │          │          │
│      │三回忌    │          │          │鈴木家    │          │          │
│      │自宅/副住 │          │          │          │          │          │
├──────┼──────────┼──────────┼──────────┼──────────┼──────────┼──────────┤
│ 3 火祝│         │          │          │          │          │          │
│  ⋮   │          │          │          │          │          │          │
└──────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

**表示内容**

| 対象 | 表示 | 見た目 |
| --- | --- | --- |
| 法要 | 施主名＋「様」、法要の種類、場所（「お寺」「自宅」）、担当（「住職」「副住」、指定なしは「2人」） | 通常の背景色。食事ありは🍱などの印を付ける |
| 葬儀の押さえ | 【葬儀】と名前 | 法要と違う背景色（例：灰色）で区別する |
| 空き枠 | 何も表示しない | 白。マウスを乗せると「＋」を表示する |

- 1つのセルに、法要1件と葬儀の押さえ1件が同時に入ることがある（R-2）。その場合はセルの中で上下に並べる。
- 土曜は青、日曜・祝日は赤の文字色にする。今日の行は背景色を変えて目立たせる。
- 1画面に収めるため、各セルの文字は最大3行に省略する。全文は予約をクリックした先で確認する。
- 想定する画面サイズは横1366px以上のPC。31日分が縦に収まらない場合は、表の見出し（時間枠の行）を上部に固定してスクロールする。

**セルをクリックしたときの動作**

| セルの状態 | クリックした場所 | 動作 |
| --- | --- | --- |
| 空き | セル | 「法要を登録」「葬儀を押さえる」の小さなメニューを出す |
| 法要のみ | 法要 | SC-03 を開く |
| 法要のみ | 空いている部分 | 「葬儀を押さえる」のみのメニューを出す（その日に葬儀がない場合） |
| 葬儀のみ | 葬儀 | SC-05 を開く |
| 葬儀のみ | 空いている部分 | 「法要を登録」のメニューを出す |
| 法要と葬儀 | それぞれ | SC-03 または SC-05 を開く |

その日にすでに葬儀の押さえがある場合（R-3）、同じ日の他のセルのメニューには「葬儀を押さえる」を出さない。

### 2.5 SC-02 / SC-03 法要予約の登録・編集

登録と編集は同じ画面レイアウトを使う。電話を受けながら1画面で入力を終えられるようにする。

```
法要予約の登録
┌──────────────────────────────────────────────┐
│ 施主の名前 *  [__________________]            │
│ 日付 *        [2026/11/20 ▼]                  │
│ 時間枠 *      ( )10時 ( )11時 ( )12時          │
│               ( )13時 ( )14時 ( )15時          │
│ 法要の種類 *  [一周忌            ▼]            │
│ 総代 *        [ ] 施主は総代さん               │
│ 場所 *        (●)お寺  ( )自宅                 │
│ 食事 *        法要後に食事をしますか？         │
│               ( )する  (●)しない               │
│ 担当          (●)指定なし（2人） ( )住職 ( )副住職│
│ 備考          [                         ]     │
│               [                         ]     │
│                                               │
│ （エラーがあればここに赤字で表示）             │
│                                               │
│        [キャンセル]          [登録する]        │
└──────────────────────────────────────────────┘
 ※編集画面では左下に [この予約を削除] ボタンを置く
```

**入力欄の動き**

| 条件 | 動き |
| --- | --- |
| 総代のチェックがない | 場所は「お寺」に固定し、「自宅」は選べない（R-6） |
| 総代のチェックを外したとき、場所が「自宅」 | 場所を「お寺」に戻す |

**エラー表示**

- 入力漏れなどは、その項目の下に赤字で表示する（例：「施主の名前を入力してください」）。
- 予約ルール違反（R-1、R-6）は、APIから返ってきたメッセージをボタンの上に表示する。入力内容は消さない。

**削除（SC-03のみ）**

- 「この予約を削除」を押すと確認ダイアログを出す。
  - 文言：「11月20日 10時 山田太郎様 一周忌 を削除しますか？」
  - ［削除する］［やめる］

葬儀の押さえ

│ 時間枠 *  ( )10時 ( )11時 ( )12時              │
│           ( )13時 ( )14時 ( )15時              │
│ 備考      [                         ]         │

### 2.7 SC-06 施主名検索

```
「山田」の検索結果（3件）
┌────────────┬──────┬────────────┬────────┬──────────┬────────┐
│ 日付       │時間枠│ 施主名     │法要    │場所      │ 担当   │
├────────────┼──────┼────────────┼────────┼──────────┼────────┤
│2027/03/05金│ 11時 │ 山田太郎   │三回忌  │お寺      │ 住職   │
│2026/11/20金│ 10時 │ 山田花子   │一周忌  │自宅      │ 副住職 │
│2025/08/10日│ 14時 │ 山田太郎   │一周忌  │お寺      │ 住職   │
└────────────┴──────┴────────────┴────────┴──────────┴────────┘
```

- 部分一致で検索する。過去の予約も含め、日付の新しい順に並べる。
- 行をクリックすると SC-03 を開く。
- 0件のときは「該当する予約はありません」と表示する。
- 検索欄が空のまま検索した場合は検索しない（「施主名を入力してください」と表示）。
- 検索対象は法要予約のみ（葬儀の押さえは含めない）。

## 3. データベース設計

### 3.1 テーブル一覧

| テーブル名 | 内容 |
| --- | --- |
| `memorial_services` | 法要予約 |
| `funeral_holds` | 葬儀の押さえ |

- 選択肢（法要の種類・場所・担当）は件数が少なく変更もほとんどないため、マスタテーブルは作らない。Rails の `enum` で管理し、DBには英語の文字列で保存する。
- 檀家台帳がないため、テーブル同士の関連はない。

### 3.2 `memorial_services`（法要予約）

| カラム | 型 | NULL | 初期値 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | × | 自動採番 | 主キー |
| `sponsor_name` | VARCHAR(50) | × | | 施主の名前 |
| `service_date` | DATE | × | | 日付 |
| `time_slot` | TINYINT | × | | 時間枠の開始時刻（10〜15） |
| `service_type` | VARCHAR(30) | × | | 法要の種類（3.4 参照） |
| `is_sodai` | BOOLEAN | × | FALSE | 施主が総代さんか |
| `place` | VARCHAR(10) | × | `'temple'` | 場所 |
| `has_meal` | BOOLEAN | × | FALSE | 法要後の食事の有無 |
| `officiant` | VARCHAR(20) | ○ | NULL | 担当。NULL は指定なし（2人で対応） |
| `note` | VARCHAR(500) | ○ | NULL | 備考 |
| `created_at` | DATETIME(6) | × | | 登録日時 |
| `updated_at` | DATETIME(6) | × | | 更新日時 |

**インデックス・制約**

| 名前 | 種類 | 対象 | 目的 |
| --- | --- | --- | --- |
| `idx_ms_date_slot` | UNIQUE | `service_date`, `time_slot` | **R-1** 法要は1枠1件 |
| `idx_ms_sponsor_name` | INDEX | `sponsor_name` | 施主名検索 |
| `chk_ms_time_slot` | CHECK | `time_slot BETWEEN 10 AND 15` | 時間枠の範囲 |
| `chk_ms_home_sodai` | CHECK | `place = 'temple' OR is_sodai = TRUE` | **R-6** 自宅は総代のみ |

### 3.3 `funeral_holds`（葬儀の押さえ）

| カラム | 型 | NULL | 初期値 | 説明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | × | 自動採番 | 主キー |
| `name` | VARCHAR(50) | × | | 名前（喪家名など） |
| `hold_date` | DATE | × | | 日付 |
| `time_slot` | TINYINT | × | | 時間枠の開始時刻（10〜15） |
| `note` | VARCHAR(500) | ○ | NULL | 備考 |
| `created_at` | DATETIME(6) | × | | 登録日時 |
| `updated_at` | DATETIME(6) | × | | 更新日時 |

**インデックス・制約**

| 名前 | 種類 | 対象 | 目的 |
| --- | --- | --- | --- |
| `idx_fh_date` | UNIQUE | `hold_date` | **R-3** 葬儀の押さえは1日1件 |
| `chk_fh_time_slot` | CHECK | `time_slot BETWEEN 10 AND 15` | 時間枠の範囲 |

法要と葬儀の押さえは別のテーブルなので、同じ枠に1件ずつ入ること（R-2）はそのまま許される。担当の重複（R-5）もチェックしない。

### 3.4 選択肢の値

| 項目 | DBの値 | 画面の表示 |
| --- | --- | --- |
| 法要の種類 `service_type` | `shijukunichi` | 四十九日 |
| | `isshuki` | 一周忌 |
| | `sankaiki` | 三回忌 |
| | `nanakaiki` | 七回忌 |
| | `jusankaiki` | 十三回忌 |
| | `jushichikaiki` | 十七回忌 |
| | `nijusankaiki` | 二十三回忌 |
| | `nijushichikaiki` | 二十七回忌 |
| | `sanjusankaiki` | 三十三回忌 |
| | `gojukkaiki` | 五十回忌 |
| | `other` | その他 |
| 場所 `place` | `temple` / `home` | お寺 / 自宅 |
| 担当 `officiant` | `jushoku` / `fukujushoku` / NULL | 住職 / 副住職 / 指定なし（一覧では「2人」） |

- 画面の表示名はフロントエンドの定数ファイル（`frontend/src/constants/options.ts`）にまとめる。APIは値（英語）だけを返す。
- 「その他」を選んだ場合、具体的な内容は備考欄に書く。

### 3.5 データの保存期間

- 過去の予約は削除せず残す（自動削除の仕組みは作らない）。
- 削除機能（F-04）は物理削除とする。キャンセルなどで職員が個別に消す場合にだけ使う。
- 予約件数は年間数百件の想定なので、数十年分たまっても性能上の問題はない。

## 4. API設計

### 4.1 共通仕様

| 項目 | 内容 |
| --- | --- |
| ベースURL | `/api` |
| 形式 | JSON（UTF-8）。リクエスト・レスポンスともキーは snake_case |
| 日付 | `YYYY-MM-DD` 形式の文字列 |
| 時刻・タイムゾーン | 日本時間（Rails の `config.time_zone = "Tokyo"`） |
| 認証 | なし（中級編でログイン機能を追加予定） |

**ステータスコード**

| コード | 意味 |
| --- | --- |
| 200 | 取得・更新に成功 |
| 201 | 登録に成功 |
| 204 | 削除に成功 |
| 400 | パラメーターの形式が不正（例：`month` が `2026-13`） |
| 404 | 指定した予約が存在しない |
| 422 | 入力エラー・予約ルール違反 |
| 500 | サーバー内部のエラー |

**エラーレスポンス（422）**

```json
{
  "errors": [
    {
      "field": "time_slot",
      "code": "slot_taken",
      "message": "11月20日 10時枠にはすでに法要の予約があります（山田太郎様 一周忌）"
    }
  ]
}
```

- `field` はエラーの原因となった項目。どの項目にも当てはまらない場合は `null`。
- `message` はそのまま画面に表示できる日本語の文。
- 400・404 も同じ形で返す。

| ステータス | `code` | `message` の例 |
| --- | --- | --- |
| 400 | `bad_request` | 年月は YYYY-MM の形式で指定してください（例：2026-11）／施主名を入力してください／リクエストの形式が正しくありません |
| 404 | `not_found` | 指定された予約が見つかりません |
| 422 | 5.2 のエラーコード、または `conflict`（5.3） | 5.2 のメッセージ |

### 4.2 エンドポイント一覧

| メソッド | パス | 内容 | 機能 |
| --- | --- | --- | --- |
| GET | `/api/calendar?month=2026-11` | 指定月の法要と葬儀の押さえをまとめて取得 | F-01 |
| GET | `/api/memorial_services?sponsor_name=山田` | 施主名で法要を検索 | F-06 |
| GET | `/api/memorial_services/:id` | 法要を1件取得 | F-03 |
| POST | `/api/memorial_services` | 法要を登録 | F-02 |
| PATCH | `/api/memorial_services/:id` | 法要を更新 | F-03 |
| DELETE | `/api/memorial_services/:id` | 法要を削除 | F-04 |
| GET | `/api/funeral_holds/:id` | 葬儀の押さえを1件取得 | F-05 |
| POST | `/api/funeral_holds` | 葬儀の押さえを登録 | F-05 |
| PATCH | `/api/funeral_holds/:id` | 葬儀の押さえを更新 | F-05 |
| DELETE | `/api/funeral_holds/:id` | 葬儀の押さえを削除 | F-05 |

### 4.3 GET `/api/calendar`

カレンダー画面は1回の呼び出しで1か月分を描画できるようにする。

**パラメーター**

| 名前 | 必須 | 例 | 説明 |
| --- | --- | --- | --- |
| `month` | ○ | `2026-11` | 表示する年月 |

**レスポンス（200）**

```json
{
  "month": "2026-11",
  "memorial_services": [
    {
      "id": 12,
      "sponsor_name": "山田太郎",
      "service_date": "2026-11-20",
      "time_slot": 10,
      "service_type": "isshuki",
      "is_sodai": false,
      "place": "temple",
      "has_meal": true,
      "officiant": "jushoku",
      "note": "参列 8名、仕出しは○○屋"
    }
  ],
  "funeral_holds": [
    {
      "id": 3,
      "name": "鈴木家",
      "hold_date": "2026-11-02",
      "time_slot": 13,
      "note": null
    }
  ]
}
```

- 並び順は日付・時間枠の昇順。
- 法要のオブジェクトの形は、以降のAPIでも同じものを使う（`created_at`・`updated_at` は省略）。

### 4.4 GET `/api/memorial_services`（施主名検索）

| 名前 | 必須 | 説明 |
| --- | --- | --- |
| `sponsor_name` | ○ | 部分一致で検索する文字列。前後の空白は取り除く。空なら 400 |

- SQL は `sponsor_name LIKE '%山田%'` とする。入力に含まれる `%` や `_` はエスケープする（Rails の `sanitize_sql_like`）。
- 並び順は `service_date` の降順、同じ日なら `time_slot` の降順。
- 件数は最大200件。それ以上ある場合は新しい順に200件を返し、レスポンスに `"truncated": true` を付ける。

```json
{ "memorial_services": [ /* 4.3 と同じ形 */ ], "truncated": false }
```

### 4.5 POST / PATCH `/api/memorial_services`

**リクエスト**

```json
{
  "memorial_service": {
    "sponsor_name": "山田太郎",
    "service_date": "2026-11-20",
    "time_slot": 10,
    "service_type": "isshuki",
    "is_sodai": false,
    "place": "temple",
    "has_meal": true,
    "officiant": "jushoku",
    "note": ""
  }
}
```

- PATCH は送った項目だけを更新する。チェックは更新後の値すべてに対して行う。
- 外側の `memorial_service` キーを省いても、項目名が合っていれば Rails が自動で包んで受け付ける（ParamsWrapper）。登録できる項目が1つもなければ 400。
- 上の一覧にない項目（`id`・`created_at` など）は無視する。
- 成功したら、登録・更新後の法要オブジェクトを返す（POST は 201、PATCH は 200）。

### 4.6 POST / PATCH `/api/funeral_holds`

```json
{
  "funeral_hold": {
    "name": "鈴木家",
    "hold_date": "2026-11-02",
    "time_slot": 13,
    "note": ""
  }
}
```

成功時のレスポンスは 4.5 と同様。

## 5. 入力チェックと予約ルールの実装

### 5.1 チェックの役割分担

要件定義書 7.4 に従い、3段階でチェックする。**最終的な判定はバックエンドとDBで行う。**

| 段階 | 目的 |
| --- | --- |
| フロントエンド | 入力の手間を減らす（入力漏れの表示、選べない選択肢を無効にする） |
| Rails のモデル | 業務ルールの正式な判定と、分かりやすいエラーメッセージの作成 |
| DB の制約 | 同時に登録された場合など、Rails のチェックをすり抜けた違反を確実に防ぐ |

### 5.2 チェック一覧

**法要予約**

| 対象 | 内容 | フロント | Rails | DB | エラーコード | メッセージ |
| --- | --- | --- | --- | --- | --- | --- |
| 施主の名前 | 必須・50文字以内。前後の空白（全角を含む）は取り除く | ○ | ○ | NOT NULL | `blank` / `too_long` | 施主の名前を入力してください／施主の名前は50文字以内で入力してください |
| 日付 | 必須・日付として正しい | ○ | ○ | NOT NULL | `blank` / `invalid` | 日付を入力してください |
| 時間枠 | 必須・10〜15 | ○ | ○ | CHECK | `blank` / `inclusion` | 時間枠を選んでください |
| 法要の種類 | 必須・選択肢の値 | ○ | ○ | NOT NULL | `blank` / `inclusion` | 法要の種類を選んでください |
| 担当 | 任意。指定するなら選択肢の値 | ○ | ○ | ― | `inclusion` | 担当を選んでください |
| **R-1** | 同じ日付・時間枠に法要がない（編集時は自分を除く） | ― | ○ | UNIQUE | `slot_taken` | 11月20日 10時枠にはすでに法要の予約があります（山田太郎様 一周忌） |
| **R-6** | 自宅は総代のみ | ○ | ○ | CHECK | `home_requires_sodai` | 自宅での法要は総代さんのみ登録できます |
| 備考 | 500文字以内 | ○ | ○ | VARCHAR(500) | `too_long` | 備考は500文字以内で入力してください |

**葬儀の押さえ**

| 対象 | 内容 | フロント | Rails | DB | エラーコード | メッセージ |
| --- | --- | --- | --- | --- | --- | --- |
| 名前 | 必須・50文字以内。前後の空白（全角を含む）は取り除く | ○ | ○ | NOT NULL | `blank` / `too_long` | 名前を入力してください／名前は50文字以内で入力してください |
| 日付・時間枠 | 法要と同じ | ○ | ○ | NOT NULL・CHECK | | |
| **R-3** | 同じ日に葬儀の押さえがない（編集時は自分を除く） | △ | ○ | UNIQUE | `day_taken` | 11月20日にはすでに葬儀の押さえがあります（13時枠） |

△：カレンダーのメニューで「葬儀を押さえる」を出さないことで防ぐ（2.4）。

R-2・R-5 は、上のチェックとテーブル設計で自然に満たされるため、個別のチェック処理は作らない。

### 5.3 同時登録への対応

2人の職員がほぼ同時に同じ枠へ登録した場合、Rails のチェックはどちらも通ってしまうことがある。その場合は、後から保存した側でDBの UNIQUE 制約違反（`ActiveRecord::RecordNotUnique`）が起きる。

- コントローラーでこの例外を受け取り、5.2 と同じエラーコード・メッセージで 422 を返す。
- メッセージに既存予約の施主名などを入れるため、例外を受け取った後にもう一度バリデーションを実行する。先に保存された予約が見つかるので、通常の重複と同じ `slot_taken`／`day_taken` のエラーになる。
- 先に保存された予約がその直後に削除されていた場合など、もう一度チェックしても違反が見つからないときは、`field: null`・`code: "conflict"`・「ほかの予約と重なったため保存できませんでした。画面を更新してもう一度お試しください」を返す。

## 7. フロントエンドの構成

```
frontend/src/
├── app/
│   ├── page.tsx                         SC-01 月カレンダー
│   ├── services/new/page.tsx            SC-02
│   ├── services/[id]/edit/page.tsx      SC-03
│   ├── funerals/new/page.tsx            SC-04
│   ├── funerals/[id]/edit/page.tsx      SC-05
│   └── search/page.tsx                  SC-06
├── components/                          カレンダー、フォーム、ヘッダーなど
├── constants/options.ts                 選択肢の値と表示名（3.4）
├── lib/api.ts                           API を呼び出す関数とエラーの変換
├── lib/validation.ts                    画面での入力チェック（メッセージは API と同じ）
└── types/                               API のレスポンスの型
```

- APIの型（`MemorialService`、`FuneralHold`、`ApiError`）は `types/` に定義し、画面とAPI呼び出しで同じ型を使う。
- APIのエラー（422）は `field` があれば該当する項目の下に、なければフォームの上にまとめて表示する。
- 祝日は `@holiday-jp/holiday_jp` を使い、フロントエンドだけで判定する（APIは祝日を返さない）。
- 予約ルール違反（`slot_taken`・`day_taken`・`home_requires_sodai`・`conflict`）は、`field` があってもボタンの上にまとめて表示する（2.5）。入力欄を直すと、その欄のエラーとボタンの上のエラーは消える。
- 開発時は `next.config.ts` の rewrites で `/api` を Rails（3001番）へ転送する。本番では Nginx が振り分ける。

**Cache Components（Activity）への対応**

この Next.js では Cache Components が有効で、画面を移っても前の画面は消えずに隠れて残る（React の `<Activity>`）。そのまま戻ると古いデータや入力内容が表示されるため、次のようにする。

| 対象 | 対応 |
| --- | --- |
| API のデータ（カレンダー・検索・編集画面） | 画面が隠れるときに捨て、再表示されたときに取り直す（`lib/use-api-data.ts`） |
| 登録・編集フォーム | 保存・削除・キャンセルのときに入力内容を初期値に戻す。日付・時間枠（URL）が変わったら作り直す。ヘッダーのリンクなどで離れた場合は、入力途中の内容を残す |
| カレンダーのメニュー | 画面が隠れるときに閉じる |
| 入力欄の `id` | 隠れた画面と重ならないよう `useId()` で作る |
| URL のパラメーターを読む画面 | `page.tsx` で `<Suspense>` に入れる（入れないとビルドが失敗する） |

## 9. インフラ設計

### 9.1 AWSリソース

| リソース | 設定 |
| --- | --- |
| リージョン | ap-northeast-1（東京） |
| VPC | 1つ（例：10.0.0.0/16） |
| パブリックサブネット | 1つ。EC2 を置く |
| プライベートサブネット | 2つ（別々のAZ）。RDS のサブネットグループに必要なため |
| インターネットゲートウェイ | パブリックサブネット用 |
| EC2 | t3.micro（メモリ 1GB）、Amazon Linux 2023、ディスク gp3 20GB（暗号化あり）、スワップ 2GB。Elastic IP を付け、停止・起動してもアクセス先のIPアドレスが変わらないようにする |
| RDS | MySQL 8.4.13（開発環境と同じ）、db.t4g.micro、シングルAZ、gp3 20GB、ストレージ暗号化あり |
| RDS のバックアップ | 自動バックアップ 1日間保持（AWS の無料プランのアカウントでは、これより長くできない）。練習用でダミーデータだけを使うため、削除保護はなし・削除時の最終スナップショットも取らない |

- 使う AWS のサービスは EC2（Elastic IP を含む）と RDS だけにし、なるべく小さいサイズにする。NAT ゲートウェイ・ロードバランサー・S3・Secrets Manager などは使わない。
- 費用の目安は 24時間動かして月 約 $36.5（RDS が約半分）。使わない期間は `terraform destroy` で消す。詳しくは `infra/README.md`。

### 9.2 セキュリティグループ

| 対象 | 方向 | ポート | 許可する相手 |
| --- | --- | --- | --- |
| EC2 | 受信 | 80（HTTP） | すべて（0.0.0.0/0） |
| EC2 | 受信 | 22（SSH） | 開発者の PC の IP アドレスのみ（`terraform.tfvars` の `my_ip`） |
| EC2 | 送信 | すべて | すべて（OSの更新などのため） |
| RDS | 受信 | 3306（MySQL） | EC2 のセキュリティグループのみ |

- サーバーの操作は SSH で行う（前回のタスク管理アプリと同じ方式）。22番は開発者の IP アドレスからだけ入れる。
- 80番はアクセス元のIPアドレスを制限しない。講師がレビューでアプリを確認できるようにするため。

### 9.3 公開方法と注意点

- ドメインは取得しない。ブラウザから `http://<EC2のパブリックIP>/` で直接アクセスする（前回のタスク管理アプリと同じ方式）。
- HTTPS化はしない。
- アクセス元の制限とHTTPS化は、講師のレビューを優先して本リリースでは行わない（要件定義書 8.3）。将来の拡張（12章）で対応する。
- この構成では、IPアドレスを知っている人は誰でも予約を見たり変更したりでき、通信も暗号化されない。そのため **本物の檀家さんの名前などの個人情報は入力せず、動作確認にはダミーデータを使う。**

### 9.4 Terraform の構成

```
infra/
├── versions.tf      Terraform・プロバイダーのバージョン
├── variables.tf     IP アドレス、インスタンスサイズ、Ruby・Node.js・MySQL のバージョンなど
├── network.tf       VPC、サブネット、ルートテーブル、IGW
├── security.tf      セキュリティグループ
├── ec2.tf           EC2、Elastic IP、SSH 鍵
├── user_data.sh     EC2 の初回起動時の準備（スワップ、Ruby・Node.js・Nginx などのインストール）
├── rds.tf           RDS、サブネットグループ、DB のパスワード
├── outputs.tf       アプリの URL、SSH のコマンド、RDS の接続先など
├── terraform.tfvars.example
└── README.md        使い方・費用の目安
```

- 前回のタスク管理アプリの Terraform 設定をもとに、必要な部分だけを流用する。
- DBのパスワードは Terraform のコードに書かない。`random_password` でランダムに作り、`terraform.tfstate` の中だけに保存する。Rails には環境変数 `DB_PASSWORD` で渡す。
- `terraform.tfstate`（パスワードを含む）と `terraform.tfvars`（実際の値）は Git に入れない。状態ファイルは開発者の PC に置く。

### 9.5 デプロイ

本リリースでは、SSH で EC2 に入って手作業でデプロイする。手順は別途 `docs/deploy.md` にまとめる。

1. `git pull` で最新のコードを取得する。
2. バックエンド：`bundle install` → `rails db:migrate` → Puma を再起動する。
3. フロントエンド：`npm ci` → `npm run build` → Next.js を再起動する。

Puma と Next.js は systemd のサービスとして登録し、サーバーの再起動時にも自動で立ち上がるようにする。

### 9.6 ログ

- Nginx・Rails のログは EC2 上に保存し、logrotate で古いものを消す。
- Rails のログでは、パラメーターの `sponsor_name`・`name`・`note` を伏せ字にする（`filter_parameters`）。個人情報を必要以上にログに残さないため（要件 8.3）。
